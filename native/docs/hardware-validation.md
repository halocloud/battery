# 硬件验收记录

随包 `verified-hardware.json` 为 `[]`，这表示尚无经本项目真机验证的组合。
单元测试中的 `MacTest,1` 仅是假硬件，不能作为发布支持记录。

## 先决条件

- 保存当前正常供电及充电状态；关闭其他限充程序和系统中的显式充电上限。
- 使用稳定的外部电源，在可观察的测试环境执行；避免无人值守验证。
- 记录 `batteryctl diagnose` 输出、机型、系统构建号、所用版本、SMC 摘要和测试时间。
- 检查诊断中 `CH0B/CH0C` 均为预期单字节类型；缺失或异常时不尝试写入。

## 验证次序

需要硬件写入的测试应在安装后的受控环境由管理员执行。先验证直接 SMC 调用，确认底层路径可用，
再登记当前组合并验证完整策略。使用的是固定安装路径下的原有 `smc`；任何失败都必须先恢复并回读允许充电状态。

1. 查询两个控制项并记录原值、类型和长度；禁止根据其他机型推断写入。
2. 对已确认的 legacy 后端，验证 `CH0B/CH0C` 的 `02` 禁充和 `00` 允许充电；同时观察系统实际充电状态和电量变化。
3. 确认两项都恢复为 `00`，并观察系统恢复允许充电。仅命令退出码或回读成功不足以通过。
4. 完成底层验证后，将下面的记录填入 root 管理的 `verified-hardware.json`，重启服务。
5. 使用 `limit` 测试到达上限禁充、降至下限恢复、中间区间保持，以及多次请求不会启动多个控制器。
6. 验证暂停、恢复、临时充满、取消临时充满、拔插电源、USB-C/MagSafe 实际使用方式。
7. 验证睡眠/唤醒、关闭终端、注销登录、重启、服务被终止，以及持久化记录的恢复。
8. 长时间插电观察；测试升级保留目标和暂停状态，卸载恢复电源控制。

## 记录格式

```json
[
  {
    "model": "填写实际机型",
    "osBuild": "填写实际系统构建号",
    "backend": "legacy-ch0b-ch0c",
    "validated": true,
    "evidence": "填写版本、时间、SMC 摘要和底层/策略/休眠测试结果的记录位置"
  }
]
```

文件路径：`/Library/Application Support/BatteryCore/verified-hardware.json`，root:wheel、0600；父目录 0700。
使用 `sudo install -o root -g wheel -m 600 已填好的记录文件 '/Library/Application Support/BatteryCore/verified-hardware.json'` 安装。
使用 `sudo launchctl kickstart -k system/local.batterycore.daemon` 重启服务读取。
系统构建号变化后必须重新验证；如果现有 SMC 后端已失效，应补充经过验证的新后端，不能把旧记录套用到新系统。

发布记录应区分“底层已验证”和完整测试结果。当前代码交付不包含已通过的硬件记录或休眠保证。
